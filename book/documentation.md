# I. Documentation 
 

**Documentation** gives relevant details about the exact processes and conditions that were used to create, collect,  process or analyse research objects. **Research objects** are any of the digital or physical materials that are created, collected, used, transformed, or generated during a research or design project. Examples of research objects include:  

- research data
- code used for analysis
- a contact list of participants
- models and simulations
- raw measurement data
- analysis code
- experimental samples or phantoms
- measurement setups
- physical prototypes
- CAD models
- 3-D printed components, etc.  

Research objects like these support or underpin research findings.    

[Place in a green box] Effective documentation provides enough relevant information that someone (either yourself or others) can understand, verify and re-use the research objects and reproduce the results.  

Documentation is like creating a recipe; an effective recipe describes with step-by-step precision how a dish was made, from start to finish. This might include exactly which ingredients were used and how much of each, how finely to chop them, in which order to add the ingredients (perhaps with an explanation of why that particular order works best), what temperature settings to cook things at, in which type of pan, for how long, how much to stir it, and perhaps describe how the dish should look and smell when it's perfectly done. That way, another cook can reproduce the exact dish if they want to. Fellow cooks can understand and appreciate the art that went into making the dish. At the same time, the documented recipe makes it possible for the original chef to retrace their steps and more easily make the dish again. Similarly, when researchers document their workflows and research objects, their goal should be to make their results reproducible and understandable by others (as well as by their later selves).  

## Relevance 

As a researcher, it is important that you provide documentation because this...   

- supports **re-usability** by providing the context needed to understand and correctly use research objects. It explains what was used/created, how it was processed or analysed, and what conditions, tools, or decisions need to be considered when using it again.
- creates **transparency of results**: documentation helps others to understand exactly how the data was obtained.
- **helps future users** (including your future self) understand the context and the process by which the data were collected.
- leads to **better collaboration** because team members can better understand the steps you took and can pick up where you left off.
- results in **less stress and mess** when it's time to write a final report because you have created a clear roadmap for your process of data collection and analysis.  


## Documentation Strategies  

While planning your project, you should define which tools you will use to document different stages of the research cycle, from data collection to processing and analysis. Here, we'll introduce and describe a variety of documentation strategies; there isn't a single “right” way to do documentation because the selected documentation tools and practices need to fit the project and process. We'll look at key questions and types of documentation that correspond to two important stages of the research project cycle. 

## Document data collection  

During and after data collection: How will you document the experimental conditions and research methods used to collect the raw data?  

You will need to select tools and practices that fit the specifics of your project; the type(s) of documentation needs to fit the processes by which you plan to collect the data. Let's look at strategies that are often used to document how data was collected or to explain features of data that's  been collected:  

 

### Ways to document data collection  

 
#### README file 

**What is it?** 
A README file is a human-readable file that provides essential information about a whole project or about individual research object(s) such as datasets and software. README files accompany a project and/or research object to ensure these can be interpreted correctly (Fuchs et al., 2018).  

 **What details are included in a README?**  

A README for a **dataset** generally includes:  
- Title of the dataset
- Creator
- Description of the dataset
- Location of data collection
- Methodology/how the data was collected
- Date(s) of data collection
- File formats
- Software or tools required to open, process, or use the files
- Relationship between files
- Access, reuse, or licence information, where relevant 

A README for a piece of **software** generally includes:   

- The name of the software
- The steps for installation
- Guidelines for contributing to the software
- The license and copyright holder
- Citation
- Acknowledgements  

 

**Good practices** 

1. It's recommended that researchers create READMEs to accompany all research objects. 

2. Use a human-readable, commonly accessible format, such as plain text (.txt) or Markdown (.md). 

3. Update the README throughout the project 

4. Use clear and consistent terminology, file names, and identifiers 

5. Keep the README close to what it's describing:  

6. A README that provides detailed information about a particular research object should be stored in the same folder as the research object that it is describing. A project-level README is stored in the root folder or main folder for a project. It describes the project, its overall folder structure, and the research objects it contains.
