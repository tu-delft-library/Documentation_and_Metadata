# I. Documentation 
 

**Documentation** gives relevant details about the exact processes and conditions that were used to create, collect,  process or analyse research objects. **Research objects** are any of the digital or physical materials that are created, collected, used, transformed, or generated during a research or design project. Examples of research objects include:  

- research data
- code used for analysis
- a contact list of participants
- models and simulations
- raw measurement data
- analysis code
- experimental samples or phantoms
- measurement setups
- physical prototypes
- CAD models
- 3-D printed components, etc.  

Research objects like these support or underpin research findings.    

[Place in a green box] Effective documentation provides enough relevant information that someone (either yourself or others) can understand, verify and re-use the research objects and reproduce the results.  

Documentation is like creating a recipe; an effective recipe describes with step-by-step precision how a dish was made, from start to finish. This might include exactly which ingredients were used and how much of each, how finely to chop them, in which order to add the ingredients (perhaps with an explanation of why that particular order works best), what temperature settings to cook things at, in which type of pan, for how long, how much to stir it, and perhaps describe how the dish should look and smell when it's perfectly done. That way, another cook can reproduce the exact dish if they want to. Fellow cooks can understand and appreciate the art that went into making the dish. At the same time, the documented recipe makes it possible for the original chef to retrace their steps and more easily make the dish again. Similarly, when researchers document their workflows and research objects, their goal should be to make their results reproducible and understandable by others (as well as by their later selves).  

## Relevance 

As a researcher, it is important that you provide documentation because this...   

- supports **re-usability** by providing the context needed to understand and correctly use research objects. It explains what was used/created, how it was processed or analysed, and what conditions, tools, or decisions need to be considered when using it again.
- creates **transparency of results**: documentation helps others to understand exactly how the data was obtained.
- **helps future users** (including your future self) understand the context and the process by which the data were collected.
- leads to **better collaboration** because team members can better understand the steps you took and can pick up where you left off.
- results in **less stress and mess** when it's time to write a final report because you have created a clear roadmap for your process of data collection and analysis.  


## Documentation Strategies  

While planning your project, you should define which tools you will use to document different stages of the research cycle, from data collection to processing and analysis. Here, we'll introduce and describe a variety of documentation strategies; there isn't a single “right” way to do documentation because the selected documentation tools and practices need to fit the project and process. We'll look at key questions and types of documentation that correspond to two important stages of the research project cycle. 

## Document data collection  

During and after data collection: How will you document the experimental conditions and research methods used to collect the raw data?  

You will need to select tools and practices that fit the specifics of your project; the type(s) of documentation needs to fit the processes by which you plan to collect the data. Let's look at strategies that are often used to document how data was collected or to explain features of data that's  been collected:  

 

### Ways to document data collection  

 
#### README file 

**What is it?** 
A README file is a human-readable file that provides essential information about a whole project or about individual research object(s) such as datasets and software. README files accompany a project and/or research object to ensure these can be interpreted correctly (Fuchs et al., 2018).  

 **What details are included in a README?**  

A README for a **dataset** generally includes:  
- Title of the dataset
- Creator
- Description of the dataset
- Location of data collection
- Methodology/how the data was collected
- Date(s) of data collection
- File formats
- Software or tools required to open, process, or use the files
- Relationship between files
- Access, reuse, or licence information, where relevant 

A README for a piece of **software** generally includes:   

- The name of the software
- The steps for installation
- Guidelines for contributing to the software
- The license and copyright holder
- Citation
- Acknowledgements  

 

**Good practices** 

1. It's recommended that researchers create READMEs to accompany all research objects. 

2. Use a human-readable, commonly accessible format, such as plain text (.txt) or Markdown (.md). 

3. Update the README throughout the project 

4. Use clear and consistent terminology, file names, and identifiers 

5. Keep the README close to what it's describing:  

6. A README that provides detailed information about a particular research object should be stored in the same folder as the research object that it is describing. A project-level README is stored in the root folder or main folder for a project. It describes the project, its overall folder structure, and the research objects it contains.

Data dictionary 

Definition: A data dictionary explains data that has been entered in a spreadsheet. It allows others to clearly interpret variable names and values (OSF Support). 

 

What details are included in a data dictionary?  

- a list of elements/variables found in the dataset 

- definitions for all codes or abbreviations used in the dataset 

- units of measure included in the dataset 

-Data types/formats 

- the source of the data  

Good practices:  

Write in clear and consistent variable names to make sure that others can understand and use the data dictionary.  

Use clear and plain language to explain each variable, explaining what it represents how it was measured or calculated.  

Specify measurement units, explain all the codes and categories used 

Record relevant measurement details 

Update the data dictionary regularly to make sure the information stays accurate as the data is processed further.

Document Your Analysis 

During data processing and analysis: How will you document your workflow to maintain a clear link between the data, your analysis method(s), and your results? 

 

You need to document how you have processed and analysed the data to arrive at research findings, particularly when your project combines different types of research objects, methods, tools and equipment. Your documentation should make it possible for someone else to understand: 

 

which data were used and how they were collected 

how the data were processed and analysed, including the methods scripts, software versions, dependencies, hardware configurations (where relevant), and analysis parameters used 

which input files produced which outputs or results 

how results presented in your final report can be traced back to the underlying data and analysis 

 

In this way, you will provide documentation for your process of analysis: by doing so, you will keep the link between your research objects, processing steps, and findings. This will help you retrace your own work, explain and justify your conclusions, and correct or update your analysis later. It also allows your instructors and classmates to understand and verify how the findings in your report were produced. 

 

Ways to document your analysis:

the generated outputs

Additional tools to document data analysis when working with codes and scripts include code comments and version control.  

To illustrate how these documentation tools can be helpful, imagine you're using code to analyse your research data. Perhaps you don't look the code for a while during an illness or a vacation. If you return to your code after several weeks, could you quickly identify the right script and understand what it does? Or could you explain to a teammate how you produced a figure? Code comments make it easier to understand, re-use and return to projects involving scripts.  

Then, to avoid losing work or confusion over which file is the latest version, using version control can help to maintain a clear history of changes. Let's look at each tool in more detail:   

 

Code comments: 

Code comments or code notes are in-line notes that you can add to source code while making changes to code and software in a terminal or command line interface.  They're not executable (they don't run with the code), but they give explanation or context about the code’s purpose, logic, and the important decisions that you've made while writing and testing the code.  

 

Good practices: 

Use comments to explain why a decision was made, especially when the reason is not obvious from the code itself.  

Document assumptions, chosen parameters, units, thresholds, data-cleaning rules and any manual decisions that affect the results.  

Do not make comments on every line. Rather, comment only on elements that may not be clear to someone reading the code.  

Keep comments up to date when you change the code; incorrect comments can be more confusing than no comments.  

For reusable functions, add a short description of what the function does, with its inputs and outputs.  

Comments do not replace a README file. Use comments for local explanations within the code. Use a README to explain the wider project, scripts, data, and dependencies. 

 

Version control:  

Version control is a way to keep a history of changes to the research software and code. It helps you identify which version of the analysis produced a particular result, compare or restore earlier versions, and collaborate without overwriting each other’s work. It can also help you maintain a traceable workflow from the original research objects through processing and analysis to the final results. 

 

Good practices:  

Use a version-control system such as Git to record changes to research software and code. Platforms such as GitHub or GitLab can be used to store and share the repository online. 

Make small, regular commits (snapshot of changes) rather than saving many changes at once. 

Add clear messages to the commits to explain what changed and why, for example 

Keep the scripts, configuration files, and documentation needed to reproduce your analysis together in the repository. 

Do not upload confidential information, personal data, passwords or sensitive project files to a public repository! 

Keep a clear link between your raw research objects, processing scripts and final results. For example, maintain a record of which input files a script uses and what outputs it produces. 

You do not need to master all Git features at once. Start by keeping a clear history of your changes and writing meaningful commit messages. 

 

Features of effective documentation  

Here, we'll look at characteristics of “good” data documentation that make research objects reproducible. We'll include a scenario for each to make these features more concrete:   

Complete: The documentation includes all details and contextual information that would be required to understand what was done and, where applicable, reproduce the testing conditions to repeat or continue the work. 

 

Scenario:  

 

A researcher is testing the load capacity (fatigue behaviour) of a new type of composite material. The experiment involves placing small samples of the composite material into a hydraulic testing machine that's connected to a software program. During testing, the software automatically records data for the samples; it collects data on the stress and strain on the specimen and temperature changes on the surface of the specimen. The researcher also uses a lab notebook to record any machine settings that could greatly impact the conditions of the experiment: for example, the temperature of the testing chamber, the loading frequency of the machine, and the amount of force that was applied during each run of the experiment. However, the researcher forgets to include the temperature of the testing chamber in the documentation file. Due to this incomplete documentation, it's not possible for others to assess the validity of the experimental results, recreate the experiment, or reproduce the results.  

 

 

Consistent: Units, names, terminology, variables are documented, and documentation practices are used consistently throughout the project. 

 

For collaborative projects, the planned documentation strategy should remain consistent across collaborators. You can imagine how confusing and unnecessarily difficult it would become if each collaborator documents differently. Thus, it's important to establish norms for documentation early on when doing projects with other people.  

 

Scenario:  

A team of researchers is collaborating to design a new sensor for measuring air quality. At the beginning of the project, the team does not establish a shared plan for documenting experimental results, design decisions, or changes to the design. Nor do they form consensus about who is responsible for maintaining the documentation or where the documentation will be stored.  

As the project develops, the team conducts experiments to test different components in the sensor. Without a unified documentation strategy, the results are recorded in a variety of different ways. Some team members keep personal notes about the conditions under which experiments were performed, while others store data in separate files and neglect to document the specific testing conditions. Some test results are discussed during meetings, but never formally recorded. And at several points, team members update the design files without documenting what was changed and why.  

At the end of the project, the team needs to write a final report explaining the development of the sensor, the experiments that were conducted, and how these results informed the final design. However, because the project was not consistently documented, the researchers struggle to reconstruct the sequence of experiments and design decisions. They have difficulty determining which experimental results support particular design choices. In some cases, they cannot establish the conditions under which earlier experiments were performed. The team therefore has to spend considerable time searching through personal notes, data files, meeting records, and different versions of the design to reconstruct the project's history. Thus, the final report is more difficult to produce and may provide an incomplete or uncertain account of how the final design was developed.  

 

This example shows how important it is to discuss plans for documentation and come to consensus within your team before you start to collect or process any research data. It can save everyone significant time and headaches.   

 

Accurate: The documentation describes exactly what was done. The documentation should be a concise but accurate description of exact steps that were followed. The level of specificity may vary from field to field.  

 

Scenario:  

A researcher provides images and instructions for the assembly of a load-bearing piece of hardware which consists of multiple components bolted together. The researcher accidentally lists the wrong size of bolts required for assembly: the researcher specifies a 6 mm bolt, but a 8 mm bolt is required. This means that anyone trying to build the piece of hardware will use undersized bolts. The too-small bolts won't be able to safely withstand the same heavy loads and force factors that were tested during the original experiment. The error in documentation could lead to accidents.  

   

 

 

Up-to-date: The documentation is maintained and updated throughout the project.   

Scenario:  

A researcher is developing software to analyse research data. The researcher uses several external libraries to build the software. Partway through the project, the researcher updates one of these libraries to a newer version. However, the researcher forgets to record the update in the project's documentation or list of software dependencies. When other researchers later try to reuse the software, they may install a different version of the library, which causes errors and produces different results. As a result, they are unable to reliably reproduce the original researcher's outputs.  

 

 

Accessible: documentation is most accessible if it is digital, machine-readable, findable, and stored in an open or commonly used format.  

 

Scenarios:  

 

A lab moved and the original documentation for a project (stored in paper notebooks) cannot be found.  

It's difficult to find the documentation file for a project because the location of the file is not clear (e.g. it's not clearly named or it's not saved next to the research object that it's describing).   

The documentation for an experiment is locked behind a paywall or a restricted access portal.  

 

 

 

To summarize, Complete, consistent, accurate, up-to-date and accessible documentation creates transparency by making it clear what was done to generate outputs, how, and why.  

 

 

Documentation in different fields  

Different scientific fields have different documentation practices.  This table shows a few examples of the types of documentation typically used in different types of projects [make this a table in the Jupyter book with column headers type of project/documentation practices]:  

Experimental research: lab notebooks, experimental protocols, instrument settings and conditions 

Data-intensive research: README files, data dictionaries, metadata standards 

Software/computational research: code comments, software READMEs, version control, computational notebooks 

Design/Hardware: CAD/design files, specifications, component lists, assembly instructions, design decisions, and version history. 

 

You do not need to invent documentation practices from scratch! Instead, you should investigate whether your discipline or community has established standards, templates, or conventions that you can follow. Here are some suggestions to learn more about documentation in your field:   

Discuss norms for documentation with your project supervisor  

Visit a repository specific to your discipline to get a sense of how researchers provide documentation for research objects within your field. Re3data helps you to find discipline-specific repositories using keywords. Try doing a search by typing your project topic into Re3data's search window.  

Ask a Data Steward. Each faculty at TU Delft has at least one data steward on staff who supports researchers with data management. Visit this Contact the Data Stewards page to find the data steward for your faculty.  

 

 

Documentation and AI  

[How] Caution and transparency are key when you have used generative AI in your workflow for a project. Transparency is also essential when you have used training data to create AI tools/models.  

 

Using AI to support documentation:  

While generative AI can be used to aid documentation and data analysis, this should be done with a high degree of caution: 

You as a user are the one responsible for the outputs, so you must always check the correctness of the outputs. You are the one who should use your expertise and critical thinking to judge the results proposed by GenAI.  

If your research involves data that originated from human participants (e.g. people's medical information including imaging and lab results, survey responses, social media posts) this data should not be fed into AI.   

If your project involves research objects that belong to someone else (e.g. a company's proprietary data) these should not be fed into AI.  

 
You can get advice on the structure, content of your documentation, and discipline-specific documentation standards from GenAI (tool for consulting). For example:  

Ask GenAI to help you create a README file or a data dictionary (but not for proprietary data, and not for data originating from humans).  

Ask GenAI to help you check and improve your documentation file.  

Ask GenAI to evaluate your documentation file and suggest how to revise it to match the documentation standards in your field or discipline.   

Ask GenAI about common documentation practices in your discipline (ex: What are laboratory notebook guidelines for [discipline]?) 

 

### Documenting use of Generative AI: 

Transparency and disclosure are key. If GenAI tools are used in the creation, processing, analysis, coding, or interpretation of research objects, you must consider what information about this use needs to be documented to make the process understandable and transparent. 

You should disclose your use of GenAI explicitly in your documentation: as part of your documentation, add information about which tool you used, on which date(s), and for which type of analysis or task(s).  

You must check for institutional policies and ask your supervisor about norms within your program.  



### Documenting the creation of AI models:   

If your project is creating AI tools/models, you should document the process of creation and make the documentation openly available. Include: 

 The intended use and context of the AI tool 

The data provenance - what data has been used for training the model and where the data comes from.  

The limitations of the tools and the accuracy of the AI tool.  

The risks of the AI tool – describe the potential biases of the model, potential harmful outputs, an assessment of the severity of these risks, and mitigation measures for the risks. 

Transparency on the model itself is also recommended by publishing the source code (properly versioned), algorithms, and parameters, at least.
